# Ongoing scrape sync runs in-process, not on an external GitHub Actions cron

`main.py` now runs `_scrape_sync()` as a background task (started from `_startup_sequence()`, same pattern as the existing `_prediction_sync` loop): every 30 minutes it calls `scraper.py`'s `sync_current_season()` directly in the backend's own process, and calls `invalidate_cache()` immediately afterward if it found new matches. `.github/workflows/scrape.yml` no longer has a `schedule:` trigger — it's `workflow_dispatch:`-only now, kept around for bootstrapping an empty DB or a manual re-scrape, not for ongoing sync.

This replaces relying on GitHub Actions' cron (`*/30 * * * 0,1,4,5,6`) as the *only* thing keeping the production DB current, per the old AGENTS.md wording. That turned out to be a real production incident, not a hypothetical: the workflow was silently auto-disabled by GitHub (`state: disabled_inactivity`) after 60+ days with no repository activity during a lull, and — unlike a *failed* run, which at least shows up red in the Actions tab — a *disabled* schedule produces no runs at all, so there was nothing to notice. The production DB was frozen at whatever the last successful run had scraped (2026-06-15) for three months. This surfaced as the prediction model reporting bye-week/rest/form stats computed off data that stopped updating after round 6, for matches many rounds later.

GitHub's schedule trigger has a second, separate reliability problem even when not disabled: it's documented as best-effort and can be delayed well past its interval under platform load, with no SLA. Neither problem is something we can configure our way out of on GitHub's side.

The backend process, on the other hand, is already kept alive continuously by an external UptimeRobot ping against `/api/health` (see the Render free-tier cold-start note in AGENTS.md) — it's already the thing whose uptime this app depends on for everything else. Moving the scrape into that same process means scrape freshness now depends on exactly one thing (this service being up) instead of two independent things (this service being up *and* GitHub's scheduler behaving), and gets a real benefit the old split-process design structurally couldn't have: `invalidate_cache()` can actually run in the same process whose in-memory `_query_cache` needs invalidating. `scrape_job.py` (the external process) calling it would only ever have cleared its own process's empty cache, not the live server's — so before this change, freshly-scraped data sat behind the 30-minute query-cache TTL regardless of how promptly the scrape itself ran.

## Considered options

Add a "last successful scrape" watchdog surfaced via UptimeRobot instead, and keep the external cron — rejected because it only makes a future outage *visible* faster; it doesn't fix GitHub's inherent scheduling unreliability, and doesn't get the same-process cache-invalidation benefit.

Run both (in-process as primary, GitHub Actions cron kept as a redundant backup) — a reasonable belt-and-suspenders option (scraping is idempotent and cheap, so redundancy isn't harmful), not chosen here because the in-process loop alone removes the actual failure mode that caused the incident, and a second scheduled trigger left in place is one more thing that could silently rot (e.g. get auto-disabled again) without anyone noticing, for no real reliability gain over just fixing the primary path. Nothing stops re-adding the `schedule:` trigger later if this service's own uptime ever becomes the weaker link.
