# nrl_client.py uses one persistent httpx client with redirects off, not a fresh client per call

`fetch_round()` and `fetch_match_detail()` used to open a brand-new `httpx.AsyncClient()` for every single call, with `follow_redirects=True`. This broke in production: NRL added an OpenID Connect "silent SSO" check in front of `/draw/data` — an unauthenticated request gets a `302` to `/account/login?prompt=none&...`, which chains to `account.nrl.com/authorize?...&prompt=none&response_mode=form_post`, and dead-ends there (a `prompt=none` OIDC check can't complete without either a real logged-in session or JS executing a form-post; neither curl nor httpx can do that). With `follow_redirects=True`, the client auto-followed the whole chain and ended up with an empty body or a small HTML page, which crashed `resp.json()`.

The fix isn't authentication. NRL's *first* redirect response also sets an anonymous cookie, `nrl_sso_probed=1` — and simply retrying the exact same URL with that cookie present succeeds directly with a `200` and real JSON, no login involved (confirmed by hand: `curl` a URL cold → `302` + `Set-Cookie: nrl_sso_probed=1` → `curl` the *same* URL again with that cookie → `200` with real data, first try, every time). It looks like a UX optimization on NRL's end (skip repeatedly bouncing real anonymous visitors through the login-check loop on every page), not a real access-control gate.

So `nrl_client.py` now keeps one module-level `httpx.AsyncClient` alive for the process's lifetime (cookie jar persists across calls) with `follow_redirects=False`, and a helper that retries the same URL once when it sees a redirect. `scraper.py`'s two clients (`scrape_all`, `sync_current_season`) got the same treatment for consistency, though the exposure there was smaller — a persistent client per scrape run already meant only the first request of each run was affected, self-healing after.

**Don't revert to a fresh client per call or turn `follow_redirects` back on** — both silently reintroduce this exact failure. If NRL changes this behavior again (the cookie name/mechanism, or an actual auth requirement), start by reproducing with `curl -D -` against `https://www.nrl.com/draw/data?competition=111&season=2026&round=1` to see the current redirect chain before touching this code.
