# DB initialisation at startup is non-fatal and retries in the background

`main.py`'s `lifespan()` used to call `init_db()` synchronously before the app could bind its port. When the DB was unreachable at boot — which happened in production when Supabase's pooler rejected the connection with `FATAL: tenant/user ... not found` (a paused free-tier project) — the whole process crashed before Render's health check could ever pass. Every deploy attempt failed identically, and the entire site (including the static frontend and `/api/health`) went dark until the DB issue was fixed *and* a fresh deploy succeeded.

We changed this so DB init runs as a background task (`_startup_sequence()`) that retries every 30s until it succeeds. The app binds its port and serves `/api/health` immediately regardless of DB state; DB-dependent endpoints return a clear error (surfaced by the frontend's `fetchJson` timeout/error UI, see ADR 0002) until the DB connects, then cache warming and prediction backfill proceed automatically.

The trade-off: a DB outage now degrades the site (some pages error) instead of taking it down outright, and errors are less immediately visible in Render's own deploy-status UI (a failed deploy is loud; a background retry loop is quiet). We chose degrade-over-die because the previous failure mode — one Supabase hiccup taking the *entire* site offline, including the ability to just show a static error page — was worse than a partially-working site, especially given this app runs on free-tier infra where that kind of hiccup (project auto-pause, pooler blips) is a real recurring risk, not a hypothetical.
